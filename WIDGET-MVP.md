# Follow-on work: widget, apps, social cards

Nothing in this file is built. It is written now because the data and brand work in this
iteration was shaped to make these possible later, and because one of them has a blocker that
has to be settled **before** any code is written, not after.

## The blocker: redistribution rights

Metals.Dev terms of service, read 2026-09-12:

> "You are authorized to publish rates provided by Metals.Dev API on websites for commercial
> purposes or for personal use, as long as you maintain an active subscription."

> "Both reselling and creating another API directly competing with Metals.Dev API is not
> allowed."

Publishing rates on **our** website is clearly permitted. A widget that other sites embed, or
a JSON endpoint other people read, sits between those two sentences: it is still our page,
but it is also our subscription feeding someone else's site. We are not going to decide that
for ourselves by reading the terms optimistically.

**Before any external embed ships, Eslam asks Metals.Dev in writing**: may we serve an
embeddable rate card that displays your rates on third-party sites, with attribution, under
our subscription? Keep the reply. If the answer is no, the widget either does not ship or
ships on a feed licensed for it.

Until then, be accurate about what `/data/prices.json` already is: a **public, same-origin
static file**. It is excluded from the sitemap and carries `X-Robots-Tag: noindex`, which
keeps it out of search results and is **not access control** — anyone who can open the site
can fetch it, and its own `usage` block saying we do not offer it to third parties is
documentation, not a lock.

So the honest position has two halves. Publishing these rates on our own website is covered by
the subscription. Whether a third party may consume the same file is **unresolved**: we have
not asked, and we will not assert either an entitlement or a prohibition we cannot point to.
What changes when we ship a widget is that we would be *offering* it for that use, which is
the thing worth asking about first.

## Widget MVP, if the rights clear

A small embeddable rate card. Deliberately modest.

- One `<iframe>` tag, fixed aspect, no script injected into the host page.
- Shows: metal, purity, price per gram in SAR, the quote time, and "Mithqal" linking to the
  matching page. Attribution is part of the card, not a hidden credit.
- Reads the same `/data/prices.json`. No provider call per embed — the request budget is
  per build, and it must stay that way however many sites embed it.
- Inherits the unhappy states: stale, market closed, time unavailable. A widget that shows a
  confident number while the feed is down is worse than no widget.
- Accessible: real text, not an image; contrast and focus states as on the site.
- `/embed/` preview page with the copy-paste snippet, excluded from the sitemap.

Why it is worth doing at all: the incumbent offers no widget, iframe or API (checked
2026-09-12), and for a price site an embed is the standard way referring domains accumulate
without asking anyone for a link. That is a **hypothesis about authority**, not a promise.
No paid links, no link exchanges, no keyword-stuffed anchors, nothing hidden — if the widget
is not worth embedding on its own, it does not get embedded.

## Mobile apps

Not built, not started. What this iteration already gives an app:

- a versioned snapshot with explicit units, purity basis, quote side, timestamps and status,
  so an app renders the same numbers with the same caveats as the site;
- one calculator contract (weight, unit, purity, optional quote and its basis) already
  specified and tested in `static/calc.js`;
- brand assets that scale: `static/icon.svg`, `icon-192.png`, `apple-touch-icon.png`,
  `og.png`, the Tajawal subsets, and the colour tokens at the top of `style.css`.

An app needs a real endpoint with a cache policy and a version negotiation, which is the same
rights question as the widget plus an availability commitment. Eslam has a Google developer
account; that is not a reason to start.

## Social cards

`static/og.png` (1200×630) ships now: the scale mark, مثقال, the English name and the domain,
on the ink band. Every page carries `og:` and `twitter:` tags whose title and description are
the page's own, generated from the registry, so a shared link never describes a different page.

A future per-day price card (the number of the day, rendered) would be generated by the same
build, from the same snapshot, with the quote time on the image. It has not been built, and
no social account exists. When one does, it says what it is: no engagement-bait price
"predictions", no "gold is rising because…" — we do not know why.
